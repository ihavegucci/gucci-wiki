# RUNBOOK — эксплуатация и инциденты

`README.md` — про разработку и как устроен CI/CD. Этот файл — про то, что делать руками,
когда что-то пошло не так на боевом сервере, или нужно провести плановую операцию (откат,
восстановление БД, ротация секрета).

## Деплой

Actions → «Build and Deploy» → «Run workflow» (вручную, без автозапуска на push — см. README).

Что происходит по шагам:
1. Сборка образа из `Dockerfile` в корне репозитория, публикация в GHCR (`:latest` и `:<sha>`).
2. Подготовка каталога деплоя на сервере (`mkdir`+`chown` под sudo, если `SSH_USER` не root)
   и копирование `deploy/*` по SSH (плоско, без структуры).
3. `setup-server.sh` — идемпотентно ставит недостающее (Docker, его compose-плагин, nginx,
   certbot), выпускает сертификат, кладёт nginx-конфиги (домен + rate limiting на
   `/api/auth/*`). Каждая привилегированная команда — под `sudo`, если `SSH_USER` не root
   (см. «Что нужно от сервера» ниже); под root — тот же скрипт, без `sudo`.
4. `docker compose pull && up -d`.
5. Ожидание `healthy` у контейнера `app` (`/api/health` — проверяет и сам процесс, и БД) —
   до 150 секунд. Если не дождались или контейнер `unhealthy` — job падает с логами
   контейнера в выводе Actions, **без автоотката**.

Неудача — смотреть: (а) лог самого job в Actions (там же — последние 100 строк
`docker compose logs app`), (б) при необходимости SSH на сервер и `docker compose logs app`
уже без ограничения по строкам. (в) Ошибка вида «create folder … failed» на шаге копирования
файлов — сервер под `SSH_USER`, не имеющим прав писать в `DEPLOY_DIR` (обычно `/opt/…`
принадлежит `root:root`) — см. «Что нужно от сервера» ниже, это чинится единственным
условием к SSH-пользователю, а не ручной командой на сервере.

## Что нужно от сервера

Единственное условие, которое workflow не может обеспечить сам: **SSH-пользователь
(`SSH_USER`) должен уже существовать и иметь либо root, либо sudo без пароля** — до первого
запуска «Run workflow». Это не наша прихоть, а неустранимое ограничение: чтобы CI сам выдал
пользователю root-права, у него эти права уже должны быть, иначе любой ключ SSH сам себя
делает root — дыра безопасности, а не автоматизация.

На практике это условие и так выполняется «из коробки» почти у любого хостера при создании
VPS с непривилегированным пользователем и SSH-ключом — отдельно ничего готовить не нужно.
Проверить на сервере: `sudo -n -l` — если строка `(ALL) NOPASSWD: ALL` (или похожая) есть,
всё готово. Если нет — добавить самостоятельно (`sudo visudo -f /etc/sudoers.d/<user>`,
строка `<user> ALL=(ALL) NOPASSWD: ALL`).

Всё остальное — Docker, плагин `docker compose`, nginx, certbot, каталог деплоя — ставит и
готовит сам workflow при каждом прогоне, идемпотентно. Если что-то из этого на сервере уже
стоит (сервер общий, не только под эту вику) — уже установленное не переустанавливается и не
перезапускается; nginx получает только свой файл `/etc/nginx/conf.d/<домен>.conf` и
`reload`, не `restart`, чужие сайты не задевает.

## Откат

Автооткат не настроен осознанно — это ручная процедура:

```bash
ssh <user>@<host>
cd /opt/gucci-wiki/deploy   # или другой DEPLOY_DIR, если задан в Secrets
# найти нужный тег в GHCR (вкладка Packages репозитория) — обычно предыдущий github.sha
sed -i 's/^APP_IMAGE=.*/APP_IMAGE=ghcr.io\/<owner>\/<repo>:<sha>/' .env
docker compose pull
docker compose up -d
```

## Восстановление БД из бэкапа

Автобэкап (раз в сутки, включается чекбоксом в `/settings` → «Резервное копирование БД»)
кладёт дампы `pg_dump -Fc` в бакет под `backups/`, хранит последние 7.

1. Скачать нужный `.dump` — кнопка в `/settings` рядом с файлом в списке.
2. Скопировать файл на сервер (`scp backup-....dump user@host:/tmp/`).
3. Остановить приложение, чтобы не писало в БД во время восстановления:
   ```bash
   docker compose stop app
   ```
4. Восстановить (`--clean --if-exists` — безопасно перезаписывает поверх существующей
   схемы, не падает, если чего-то ещё нет):
   ```bash
   docker compose exec -T postgres pg_restore --clean --if-exists -U gucci -d gucci_wiki < /tmp/backup-....dump
   ```
5. Запустить приложение обратно:
   ```bash
   docker compose start app
   ```
6. Проверить, что вика открывается и данные соответствуют ожидаемой точке восстановления.

**Процедура проверена целиком** (2026-09-11), не только на бумаге: снят
`pg_dump -Fc` с рабочей базы, восстановлен командой из пункта 4 в отдельный
пустой Postgres, на нём поднято приложение. Результат: `pg_restore` отработал
без единого предупреждения, все счётчики строк совпали, и — что важнее —
уцелело то, что при неаккуратном восстановлении теряется молча: FTS-триггер
`page_search_sync`, функция `gucci_strip_html`, частичный уникальный индекс
`FileFolder_root_name_key`, все 36 индексов и история миграций Prisma.
Приложение на восстановленной базе стартовало (`/api/health` → 200), поиск
находил статьи (значит, полнотекстовый индекс живой), страницы, история
версий и админка пользователей открывались.

Если будете повторять проверку — делайте её на отдельном контейнере, а не
поверх рабочей базы: `--clean` сначала удаляет объекты, и обрыв на середине
оставит базу разрушенной.

```bash
# одноразовый Postgres рядом с рабочим стеком
docker run -d --name restore-test --network gucci-wiki_default   -e POSTGRES_USER=gucci -e POSTGRES_PASSWORD=gucci -e POSTGRES_DB=gucci_wiki postgres:16-alpine
docker exec -i restore-test pg_restore --clean --if-exists -U gucci -d gucci_wiki < backup-....dump
# приложение на восстановленной базе
docker run -d --name restore-app --network gucci-wiki_default   -e DATABASE_URL="postgresql://gucci:gucci@restore-test:5432/gucci_wiki"   -e SESSION_SECRET="любая-строка" -e NODE_ENV=production gucci-wiki-app:local
docker rm -f restore-app restore-test   # убрать за собой
```

## Где лежат секреты

**GitHub Secrets репозитория** (Settings → Secrets and variables → Actions → Secrets, полный
список и описание каждого — README, раздел «CI/CD и деплой»):
обязательные — `SSH_HOST`, `SSH_USER`, `SSH_KEY`, `POSTGRES_PASSWORD`, `SESSION_SECRET`,
`SETTINGS_KEY`, `DOMAIN`, `LETSENCRYPT_EMAIL`, `APP_PORT`; необязательные — `DEPLOY_DIR`,
`CRON_SECRET`.

**На сервере** — `$DEPLOY_DIR/.env`, генерируется CI заново при каждом деплое, не хранится
в git.

**S3-ключи и Telegram-токен** — только в БД (таблица `Settings`), вводятся через `/settings`
в интерфейсе, никогда не попадают в `.env`/git. Шифруются на уровне приложения (AES-256-GCM)
ключом из переменной окружения `SETTINGS_KEY` — см. следующий раздел.

## `SETTINGS_KEY` — шифрование секретов в БД

Зачем: суточный автобэкап БД уезжает в тот же S3-бакет, что и файлы вики. Без шифрования
утечка одного дампа отдаёт разом и доступ к бакету, и токен бота.

Как включить (это отдельный, необязательный шаг — без него всё работает как раньше):

1. Сгенерировать ключ: `openssl rand -base64 48`.
2. Добавить его в GitHub Secrets как `SETTINGS_KEY`, прописать в блок генерации `.env` и в
   список `envs:` шага `Deploy over SSH` в `.github/workflows/deploy.yml` (рядом с
   `SESSION_SECRET`). В обоих `docker-compose.yml` переменная уже проброшена.
3. Задеплоить и **один раз пересохранить** в `/settings` ключи S3 и токен бота: старые
   открытые значения продолжают читаться как есть, а шифротекст появляется только при
   первом сохранении.

Важные свойства:

- Переменная не задана — секреты пишутся и читаются открытым текстом, приложение работает
  ровно как до появления шифрования. Обязательной она не является.
- Формат хранения самоописательный: `enc:v1:<iv>:<tag>:<ciphertext>` в base64. Значение без
  этого префикса считается ещё не зашифрованным.
- **Ключ потерян или заменён на другой** — данные вики (статьи, файлы, пользователи) целы,
  БД читается как обычно. Недоступными становятся только три поля: ключи S3 и токен бота
  показываются в `/settings` как «не настроено», загрузка/скачивание файлов и Telegram
  молчат. Лечение — ввести значения заново в `/settings` (перевыпускать их у провайдера при
  этом не нужно, если утечки не было). В логах приложения об этом будет одно сообщение
  `[settings] не удалось расшифровать поле ...` (одно за запуск, не на каждый запрос).
- Ротация ключа = ровно тот же сценарий: поменять `SETTINGS_KEY`, задеплоить, ввести
  S3-ключи и токен бота заново. Отдельной процедуры перешифрования нет.

## При подозрении на утечку

Ротация — по каждому типу секрета отдельно, не «поменять всё разом»:

- **SSH-ключ деплоя** — сгенерировать новую пару, добавить публичную часть в
  `~/.ssh/authorized_keys` на сервере, обновить `SSH_KEY` в GitHub Secrets, удалить старую
  запись из `authorized_keys`.
- **`SESSION_SECRET`** — обновить Secret, задеплоить. Инвалидирует **все** текущие сессии
  пользователей разом — ожидаемо, не баг; стоит заранее предупредить сотрудников, что их
  сегодня разлогинит.
- **`POSTGRES_PASSWORD`** — обновить Secret **и** пароль самого пользователя в контейнере
  (Compose не меняет пароль существующего volume автоматически):
  ```bash
  docker compose exec -T postgres psql -U gucci -c "ALTER USER gucci WITH PASSWORD '<новый>';"
  ```
  затем обновить Secret в GitHub и передеплоить.
- **S3-ключи / Telegram-токен** — перевыпустить в соответствующем провайдере/BotFather,
  вписать новые значения через `/settings` (старые значения нигде, кроме БД, не хранятся).
- **`SETTINGS_KEY`** — сгенерировать новый, обновить Secret, задеплоить и ввести S3-ключи и
  токен бота заново в `/settings` (см. раздел выше). Сами S3-ключи и токен при этом
  перевыпускать не обязательно — если утёк только ключ шифрования, а не дамп БД.

## Оповещения о состоянии сервера

Приложение раз в час само проверяет четыре вещи и пишет о них в Telegram всем админам,
у которых активирован бот (`lib/monitoring/`, таймер — в `instrumentation-node.ts`):

| Проверка | Внимание | Тревога |
| --- | --- | --- |
| Свободное место на диске | меньше 15% | меньше 5% |
| Срок TLS-сертификата (домен из `APP_ORIGIN`) | осталось ≤ 14 дней | ≤ 3 дней |
| База данных отвечает | — | нет ответа за 5 с |
| Автобэкап (если включён) | — | ошибка последнего прогона или он старше двух суток |

Сообщение приходит при **смене** состояния (в том числе «восстановлено») и не чаще раза в
сутки, пока проблема держится. Настраивать нечего: если Telegram-бот не настроен или ни один
админ его не активировал — оповещения просто не отправляются (в лог пишется одна строка).
`APP_ORIGIN` пуст или начинается с `http://` — проверка сертификата пропускается.

**Чего здесь нет:** оповещения «сайт упал». Изнутри собственного процесса это невозможно —
умер процесс, умер и таймер, который должен был сообщить. Нужен внешний наблюдатель
(любой uptime-сервис, проверяющий `https://<домен>/api/health` раз в минуту); эндпоинт для
этого уже есть и авторизации не требует.

## Как проверить, что автобэкап работает

1. `/settings` → «Резервное копирование БД» → включить чекбокс (требует уже настроенного и
   сохранённого S3-бакета выше на той же странице).
2. Тик таймера — раз в сутки, **не немедленно при включении** (`setInterval` внутри
   `instrumentation-node.ts` ждёт полный интервал от старта процесса, не от момента
   включения флага). Для быстрой проверки без ожидания суток — перезапустить контейнер
   `app` (`docker compose restart app`) и подождать чуть больше интервала одного тика.
3. Обновить `/settings` — «Последний бэкап» должен показать свежую дату и «успешно», в
   списке — новый файл `backup-....dump` разумного размера (не 0 байт). Ошибка вместо
   «успешно» — текст ошибки виден прямо там же (обычно — S3 недоступен или неверные ключи).
